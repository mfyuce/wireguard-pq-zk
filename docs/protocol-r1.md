# wgzk protocol, revision R1

Status: frozen 2026-09-29. This document is the contract between the kernel module
(`wireguard-6.8/`), the daemon (`userspace/wg-zk-daemon/`) and the paper. Where the code
and this document disagree, the code is wrong.

It replaces the behaviour of commit `0730323`, which differed from the paper in five
places: the client's long-term WireGuard key travelled in every initiation; the gateway
decapsulated and installed keys before any proof was verified; no replay memory existed;
the challenge bound neither the credential public key nor anything else of the session;
the TLS handshake signature was never verified and TLS 1.2 was enabled.

## 1. Terms

| Term | Meaning |
|---|---|
| Connection | The period during which a client uses one WireGuard key pair towards one gateway. One initial handshake, any number of re-keys. |
| Re-key | A handshake inside a connection. Same session key, same tunnel address. Re-keys of one connection are linkable to each other by design. |
| Session key `S_c` | The client's per-connection WireGuard static key pair. It has no long-term meaning. |
| Credential epoch | Validity period of one group credential `(sk_e, pk_e)` and of one gateway KEM key pair, numbered by a 32-bit counter. |
| Mode | `0x01` ZK-only, `0x02` ZK+PQ. A gateway runs in exactly one mode. |

## 2. Keys

| Key | Held by | Lifetime | Provisioned |
|---|---|---|---|
| `sk_e` (Ristretto255 scalar) | every client of the group | epoch | enrolment channel |
| `pk_e = [sk_e]G` | gateway | epoch | enrolment channel |
| `S_gw` (WireGuard static) | gateway; public half known to clients | long | enrolment channel |
| `ek` / `dk` (ML-KEM-768) | clients / gateway | epoch | enrolment channel |
| TLS certificate (ECDSA P-256) | gateway; fingerprint known to clients | long | enrolment channel |
| `S_c` (WireGuard static) | one client | one connection | generated by the client |

## 3. Wire formats

### 3.1 Initiation, UDP, type `0xA1`, 244 bytes

Unchanged: Noise IK first message (`sender_index`, ephemeral, `encrypted_static`,
`encrypted_timestamp`), then `zk_r[32]`, `zk_s[32]`, `zk_nonce[32]` in clear, then the two
MACs. `encrypted_static` now carries `S_c`.

### 3.2 Side channel, TLS 1.3 over TCP 51821, client to gateway, 1124 bytes

`token (u32 LE) || nonce (32) || ct (1088)`. One message per connection attempt. The
gateway sends nothing back. TLS 1.3 only; no client certificate; no resumption; no ALPN;
fixed server name `wgzk-gateway`. The client checks the certificate fingerprint **and**
the handshake signature.

### 3.3 Challenge (version 2)

```
c = SHA-512( T || mode || epoch || pk_e || S_gw || S_c || R || nonce || h_ct )  mod l
```

| Field | Bytes | Content |
|---|---|---|
| `T` | 28 | ASCII `WGZK-v2/schnorr-ristretto255`, no terminator |
| `mode` | 1 | `0x01` or `0x02` |
| `epoch` | 4 | u32, little endian |
| `pk_e` | 32 | compressed Ristretto255 |
| `S_gw` | 32 | gateway WireGuard public key |
| `S_c` | 32 | client session public key |
| `R` | 32 | commitment, compressed Ristretto255 |
| `nonce` | 32 | session nonce |
| `h_ct` | 32 | `SHA-256(ct)` in mode `0x02`; zero bytes in mode `0x01` |

Response `s = r + c * sk_e mod l`. The proof on the wire is `(R, s, nonce)`.

Binding `S_c` is required for soundness: the proof travels in clear, and a proof that is
not bound to the session key could be copied into an attacker's initiation.

### 3.4 PSK

`psk = SHA-256("wgzk-mlkem-psk-v1" || ss)`.

### 3.5 Tunnel address

Inner IPv6, derived by both sides:
`addr = prefix (8 bytes) || SHA-256("wgzk-addr-v1" || S_c)[0..8]`.
Default prefix `fd57:475a:4b00:0000::/64`. The client assigns `addr/128` to its interface;
the gateway sets the peer's allowed-ips to `addr/128`.

## 4. Netlink family `wgzk`, version 2

Operations require `GENL_UNS_ADMIN_PERM`, that is `CAP_NET_ADMIN` over the user namespace
that owns the network namespace of the caller. This is the rule of WireGuard's own
configuration interface: who may add a peer to a device may also decide about its
handshakes. A verdict reaches only initiations that arrived on a device in the network
namespace of the caller. Events are multicast to the network namespace of the WireGuard
device only.

| Attribute | Id | Type | Meaning |
|---|---|---|---|
| `PEER_INDEX` | 1 | u32 | sender index of the initiation (informational) |
| `RESULT` | 2 | u8 | verdict, 1 accept, anything else reject |
| `PEER_ID` | 3 | u64 | kernel peer id (initiator side) |
| `R` | 4 | bin 32 | commitment |
| `S` | 5 | bin 32 | response |
| `IFINDEX` | 6 | u32 | interface index |
| `PEER_PUB` | 7 | bin 32 | static public key of the remote party |
| `TOKEN` | 8 | u32 | correlation token |
| `SESSION_NONCE` | 9 | bin 32 | session nonce |
| `PENDING_ID` | 10 | u64 | kernel-assigned id of a deferred initiation |
| `LOCAL_PUB` | 11 | bin 32 | static public key of the local interface |

| Command | Id | Direction | Attributes |
|---|---|---|---|
| `SET_PROOF` | 2 | daemon to kernel | `PEER_ID`, `IFINDEX`, `R`, `S`, `SESSION_NONCE`, optional `TOKEN` |
| `NEED_PROOF` | 3 | kernel to daemon | `IFINDEX`, `PEER_ID`, `PEER_PUB` (= `S_gw`), `LOCAL_PUB` (= `S_c`), `TOKEN` |
| `SET_VERIFY` | 4 | daemon to kernel | `PENDING_ID`, `RESULT` |
| `NEED_VERIFY` | 5 | kernel to daemon | `IFINDEX`, `PENDING_ID`, `PEER_INDEX`, `PEER_PUB` (= decrypted `S_c`), `LOCAL_PUB` (= `S_gw`), `R`, `S`, `SESSION_NONCE` |

Command 1 (`VERIFY`, legacy) is removed. `SET_VERIFY` without `PENDING_ID` is rejected.
All eight attributes of `NEED_VERIFY` are mandatory; a daemon drops an event that lacks
one.

## 5. Client

Per connection: generate `S_c`, set it as the interface key, take a new UDP port,
configure the address of Section 3.5 (`wg-zk-daemon new-connection --iface <name>`). One interface per gateway,
because the key belongs to the interface. When the key of an interface changes, the kernel
discards a proof that it still holds for a peer of that interface, since the proof is bound
to the old key, and may ask for a new one at once.

The kernel asks for a proof (`NEED_PROOF`) when it has to send an initiation and holds no
proof for the peer, at most once per 5 s per peer while the request is unanswered. A proof
is used for one initiation. A retransmission asks for a new proof and, in mode `0x02`,
causes a new ciphertext.

Per handshake, on `NEED_PROOF`:

1. Draw `nonce`. In mode `0x02` encapsulate to `ek`, giving `(ct, ss)`.
2. Compute the proof over `S_gw = PEER_PUB` and `S_c = LOCAL_PUB` as delivered by the
   kernel in this event.
3. Mode `0x02`: send the side-channel message; install `psk` for the gateway peer.
4. If any part of step 3 failed: stop. No `SET_PROOF`; the handshake times out.
5. `SET_PROOF`. The kernel sends the initiation.

Peers and keys are written through WireGuard's own netlink interface, inside the daemon
(`WGZK_INSTALLER=netlink`, the default, on both sides). `WGZK_INSTALLER=tool` runs the `wg`
tool instead, one process per handshake. `new-connection` uses the `wg` and `ip` tools; it
is not part of a handshake.

## 6. Gateway

1. Side channel: accept, read 1124 bytes, store `nonce -> (ct, token, arrival)` in the
   ciphertext buffer. No decapsulation, no key installation.
2. Kernel, on `0xA1`: MAC and cookie check as in WireGuard; decrypt `S_c`; store the raw
   initiation under a fresh `PENDING_ID`, whether or not `S_c` names a known peer; emit
   `NEED_VERIFY`; release every lock and reference it took and wipe key material.
3. Daemon, on `NEED_VERIFY`. A decision on the same nonce that is in progress makes the
   daemon reject at once (`busy`), and so does a full set of decisions in progress
   (`overload`): copies of an initiation are not queued.
   1. reject if `nonce` is in the replay cache;
   2. mode `0x02`: look up `ct` for `nonce`, waiting at most `T_wait`; reject if absent.
      The lookup does not remove the entry. It leaves the buffer when a handshake for
      its nonce is accepted, or when it expires. Otherwise an initiation that merely
      copies a nonce it has seen on the wire would use up the ciphertext of the
      handshake it copied from;
   3. verify the proof for the current epoch, then for the previous epoch if one is
      configured;
   4. mode `0x02`: decapsulate, derive `psk`;
   5. create or update the peer `{S_c, psk, allowed-ips}`;
   6. insert `nonce` into the replay cache.
4. `SET_VERIFY(PENDING_ID, 1)`. The kernel re-consumes the stored initiation, which now
   finds the peer, and answers. The endpoint of the peer is updated only at this point.
5. Any failure in step 3: `SET_VERIFY(PENDING_ID, 0)`. Nothing is created.

Type-1 initiations (plain WireGuard) are dropped while the module parameter
`require_zk` is set, which is the default.

At start the gateway daemon enters the peers that the interface already has into its peer
table, as if they had been verified at that moment (`WGZK_ADOPT_PEERS`, default 1). They
count against the bound and are removed when idle. The interface is therefore reserved for
peers that the daemon creates: a peer configured by hand would be removed as well.

### Acceptance rule

A handshake is accepted if and only if the proof is valid for the current or the previous
epoch, its nonce has not been accepted before in this epoch, it is bound to the session
key of the initiation and, in mode `0x02`, to the ciphertext the gateway holds for the same
nonce, and the key derived from that ciphertext was installed. Otherwise no peer, no key
and no response is produced.

Wire order and processing order differ. The ciphertext normally reaches the gateway
before the proof. The guarantee concerns what the gateway does, not what arrives first.

## 7. Bounded state

| State | Default bound | Default expiry | Setting |
|---|---|---|---|
| Kernel pending table | 1024 entries | 5 s | module parameters `pending_max`, `pending_timeout_ms` |
| Ciphertext buffer | 1024 entries | 5 s | `WGZK_CT_BUFFER_MAX`, `WGZK_CT_TTL_MS` |
| Side-channel connections | 256 at a time | handshake 2 s, read 1 s | `WGZK_TLS_MAX_CONN`, `WGZK_TLS_HANDSHAKE_MS`, `WGZK_TLS_READ_MS` |
| Wait for ciphertext | | 250 ms | `WGZK_CT_WAIT_MS` |
| Decisions in progress | 1024 | | `WGZK_VERIFY_MAX` |
| Replay cache | 1,048,576 nonces | end of epoch (process lifetime) | `WGZK_REPLAY_MAX` |
| Dynamic peers | 4096 | idle 300 s | `WGZK_PEER_MAX`, `WGZK_PEER_IDLE_SECS` |
| Requests to the WireGuard netlink interface, calls of the `wg` and `ip` tools | | 5 s | fixed |

When a bound is reached the new item is refused. Nothing is evicted to make room, because
eviction would let an attacker push out legitimate state.

No WireGuard peer and no key exists before a proof verifies. Stored initiations and
buffered ciphertexts are state; that is why they are bounded.

## 8. What the implementation reports

For tests and measurements; none of this is an interface.

- The module counts events in debugfs, `wgzk/stats`: `pending` (entries in the table now),
  `proof_requests`, `proofs_set`, `deferred`, `refused_full`, `undecryptable`, `accepted`,
  `refused_handshake`, `rejected`, `expired`, `late_verdict`, `legacy_dropped`.
  `wgzk/pending` lists the stored initiations.
- The daemon writes one line per handshake:
  `[timing] side=client token=.. nonce_prefix=.. result=ok|fail [reason=..] zk_us=.. encap_us=.. tls_us=.. write_us=.. psk_us=.. tail_us=.. total_us=..`
  and
  `[timing] side=gateway pending_id=.. token=.. nonce_prefix=.. result=ok|fail [reason=..] wait_ct_us=.. verify_us=.. decap_us=.. peer_us=.. total_us=..`.
  `nonce_prefix` is the first four bytes of the session nonce, which travels in clear.
  Reasons at the gateway: `busy`, `overload`, `replay`, `replay_full`, `no_ct`, `proof`,
  `peer_full`, `peer_install`, `verdict_lost`. Reasons at the client: `rng`, `tls_connect`,
  `tls_timeout`, `send`, `send_timeout`, `psk`, `queue`.
- A daemon built with the cargo feature `fault-injection` misbehaves in the one way that
  `WGZK_FAULT` selects (`userspace/wg-zk-daemon/src/fault.rs`). The released daemon
  contains none of it and refuses to start when `WGZK_FAULT` is set.

## 9. Known limits of this revision

- The replay cache lives in memory. After a daemon restart inside an epoch, an old
  initiation whose peer has been collected can recreate that peer. The attacker does not
  hold the session key, so the peer is unusable; it occupies a slot until it is collected.
  In mode `0x02` the ciphertext of the old initiation is gone as well, so the initiation is
  refused.
- Authorisation is classical. An adversary with a quantum computer can compute `sk_e` from
  `pk_e` and forge proofs. Epochs bound the credential of a revoked member, nothing more.
- No post-quantum forward secrecy inside an epoch: whoever later obtains `dk` and can break
  X25519 can open the recorded sessions of that epoch.
- The gateway never initiates a handshake towards a dynamic peer. Its kernel may ask for a
  proof when WireGuard's timers want a new handshake; the gateway daemon does not answer,
  and nothing is sent.
- The daemon writes a log line for every refused connection and ciphertext. Under a flood
  the log is the largest cost.
- The kernel table is shared by all wgzk interfaces of a host; its bound is not per
  interface.
- Re-keys open a new TLS connection each time.
